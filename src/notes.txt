REST = Using standard HTTP methods (GET, POST) on URLs to interact with data.


1) first of all, our web server app will have to handle user requests. This request can be of many types, like get, post, put, delete etc. A request comes with a label (path: where to look) and 
an action (method: what to do). So in order to handle this request, we need to create routes. Each route will have its own label(path) and action(method). when a request will match with a route,
itll run the handler function declared specifically for that route (path,method).
        lets create a route to handle a certain type of request:

let router01 = Router::new()
    .route("/vehicle",get(vehicle::vehicle_get));

2) in order to receive the requests from other pc, server, we need a connection port in our server. we will take that from the os. First we create a string which contains an ip and port number.
then using that string location we occupy that port from the os.
let address = "0.0.0.0:6750";
let listener = tokio::net::TcpListener::bind(address)
    .await.unwrap();

3) then we connect the router with the listener. anything coming to the listener will now go to the router1. 
to do this we do - axum::serve(listener,router01).await.unwrap();

Now, when an user sends request through that listener:
a- receiving: the listener catches a raw TCP connection and hands that to axum::serve
b- analyzing: axum::serve translates that into proper http request. It looks for the path and method.
c- dispatching: it checks the router1, if theres is a route combining that exact path and method, it calls the handler function.
d- responding: once the handler is done and returned any result, axum::serve packages the result into an http response and send it back out through the listener to the user.
listener catches RaW tcp, sends that to axum::serve-> tcp is translated to HTTP request, the path and method is determined -> matches the routes, upon  match handler is executed -> result of the
handler is sent to the caller as a http response

async fn vehicle_post(Json(mut V): Json<Vehicle>) -> Json(vehicle). 
a. (Json(V): Json<Vehicle>) : this is the Extractor. It looks at the body of the http request. It takes the raw JSON text sent by the user. It Deserializes it, turning that text into a Rust struct instance named V.
b. -> Json(Vehicle) : This is the Return Type. It defines what the HTTP Response Body will look like. Axum will take our return value, Serialize it back into JSON text, and send it to the user
with the correct headers. For this to work, our Vehicle struct must have both Serialize and Deserialize derived at the top.

upon a call to this fn, the Deserialization internally happens, and we get the Struct saved in V. 
now we can update V. like V.manufacturer = "xDD".to_string(), V.id = Some(uuid::Uuid::new_v4().to_string());
then we can return V wrapped in Json. return Json(V). this will Serialize V into JSON text and send it to the user.

6) If we move the data from the Request Body to the URL (Query String), the "tool" (extractor) we use in our function signature must change to match.

2. How the Rust Handler Changes

************* make shared list for all routes

now our goal is to share a single list across multiple requests safely (Thread safety).
The Goal: Make it so when we POST a vehicle, and then call GET, the new vehicle actually shows up in the list.

first we create a new router3, make new route -> give it a path /vehicle_save, and vhicle_rec() handler as post method.

we want to save the data we get from POST request, in this case, vehichle objects. Since every request in axum uses a seperate thread, we cant use a normal vector(vec)
To do this, we use three tools together:
Vec<Vehicle>: The actual list of cars.
Mutex: The "Lock." Only one thread can change the list at a time (prevents data corruption).
Arc: The "Smart Pointer." It allows multiple threads to "own" the same list.

we need to create the state and inject it into our router, so all our handlers can see it.
so in mian.rs we import Arc,Mutex, and State from ax_um.
then we define a state; type SharedState = Arc<Mutex<Vec<Vehicle>>>;
type- keyword for creating a type alias
SharedState- the name of the type we are making
= - means the name it alias for
Arc<Mutex<Vec<Vehicle>>>- the actual type being aliased
now we can create variable of this SharedState type.

inside main, we initialize our databse, in this case the empty list.
let shared_state = Arc::new(Mutex::mew(Vec::new()));
it's a thread-safe, persistent in memory database that survives across requests, accessible from all our API endpoints.
Vec::new() — Creates an empty list/collection (this is our "database table")
Mutex::new(...) — Wraps it in a lock so only one async task can modify it at a time (thread-safe access)
Arc::new(...) — Allows multiple async tasks to share and access the same database
then we provide the state to the router. let final_router = final_router.with_state(shared_state); 
so each time a request matches with any of these routes, automatically grab this state and hand it to the handler functions. all our route handlers can access the same shared database.
listener remais same.

now while writing the vehicle_rec function, we do this:
pub async fn vehicle_rec( State(state) : State<SharedState> , Json(v): json<Vehicle> ) 
by this we bind the State in state variable which was declared in main and was provided to all the routes using with_state(shared_state) method. later in powerShell invoke method,
we dont need to pass state. so all we will receive is a Json payload, extract it to the struct v.
inside the function, state holds the Arc<Mutex<Vec<Vehicle>>> which is the shared vault passed from main. 
now we declare let mut db = state.lock().unwrap(); 
lock() acquire the lock on the Mutex, then unwrap() extracts the handle to db
db is now the exclusive temporary handle to the shared vector database.
now we can do db.push(v.clone());  //cause we will return v later, we need to clone it   
then we return that v wrapped in Json.

so now we can save objcts in our server. lets create a get method which will read this list.

we create a new route in router03. saved_vehicle() handler as GET method.
off course we can access the shared vector databse in this function, but like before we need to accept it in a variable, then lock the mutex to get the handle of vector database.

Registration: We save the Hash.
Phase 1: Security Foundations (The "Vault")
Focus: Secure user creation and data modeling.
Step 1: Add bcrypt or argon2 to Cargo.toml.
Step 2: Define the User struct. Include id, username, password_hash, and a Role enum (Admin/User).
Step 3: Expand AppState to include a Mutex<Vec<User>>.
Step 4: Create the /register POST route.
Logic: Check if username exists -> Hash password -> Push to User Vec.
Outcome: You can create users via PowerShell. If a hacker steals your "database" (the Vec), they only see scrambled gibberish instead of actual passwords.

Login: We verify the Hash and return a Token.
Phase 2: Identity & Session (The "Key Card")
Focus: Authentication and the "Stateless" handshake.
Step 1: Add the jsonwebtoken (JWT) crate.
Step 2: Create a /login POST route.
Logic: Find user by name $\rightarrow$ Compare hashed password $\rightarrow$ If match, generate a Signed JWT.
Step 3: Define "Claims." This is the data inside the token (like user ID and expiration time).
Step 4: Return the JWT string to the PowerShell client.
Outcome: Your server now issues "Digital Passports." PowerShell can store this token in a variable: $token = $response.token.

for the phase 2, we will make the login system. a user will give us username and password. we will match those with the users stored in Vec<user>.
if we get a match, we will make a claim for the user. in the claim struct, we will give user_id, creation time, expiration time. 
then we make a Json web token using the encode(). encode will tkae a header,the claim and a signature made of the secret key. 
then we return that token in a response.





Phase 3: The "Bouncer" (Middleware & Authorization)
Focus: Protecting your vehicle data and checking permissions.
Step 1: Implement an Axum Extractor (the "Bouncer"). This is a function that looks at every incoming request's header.
Step 2: Validate the Token. If the header Authorization: Bearer <token> is missing or fake, return 401 Unauthorized.
Step 3: Implement Role-Based Access Control (RBAC).
Example: Anyone can GET vehicles, but only Role::Admin can POST or DELETE them.
Step 4: Wrap your existing vehicle routes with this middleware.
Outcome: Your /vehicle_save route is now locked. If you try to use it without a valid "Admin" token, the server rejects you immediately.

Phase 4: Persistence & Logging (The "Permanent Record")
Focus: Moving from RAM to a real Database and tracking events.
Step 1: Add sqlx and tokio-postgres (or SQLite).
Step 2: Replace Vec<Vehicle> and Vec<User> with SQL queries. No more Mutex—the database handles the "locking" for you.
Step 3: Add the tracing crate. This is professional-grade logging.
Step 4: Set up "Audit Logs." Every time an Admin deletes a vehicle, the server writes a log: "User 5 deleted Vehicle X at 14:00".
Outcome: Your server can crash or restart, and your cars and users will still be there. You have a full "paper trail" of every action taken in the system.
